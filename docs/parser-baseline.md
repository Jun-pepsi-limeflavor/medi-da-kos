# Medidakos 파서 추출 정확도 평가 기준선 (Parser Baseline)

**작성일:** 2026-08-27  
**기준 문서:** `docs/backoffice-spec.md` (6.3, 6.4), `docs/plans/2026-08-26-parser.md` (Task 5)

## 1. 개요 및 평가 목적

Medidakos 백오피스의 수신 인바운드 메일 파서 엔진은 메일 본문과 메타데이터에서 바이어 요구사항 및 딜(Deal) 제안 필드를 추출하여 `messages/{id}.extraction`에 제안값 형태로 저장합니다.

본 평가 기준선 문서의 목적은 다음과 같습니다:
1. **정량적 기준선 확립:** "좀 나아진 것 같다"는 주관적 감각 대신, 명확한 수치에 기반한 모델/프롬프트 개선 반복 주기 구축.
2. **회귀(Regression) 방지:** 프롬프트 문구를 수정하거나 모델 버전을 변경할 때, 기존에 잘 동작하던 사내 핵심 케이스들이 깨지지 않는지 지속 점검.
3. **신뢰 경계 확립:** LLM 출력은 신뢰 경계 바깥에 있으므로, 사람이 검토하고 확정한 값을 기준으로 파서의 정확도와 한계를 투명하게 관리.

## 2. 평가 방법론: `accepted`를 Ground Truth로 활용

별도의 인위적 테스트 픽스처 제작이나 수동 라벨링 데이터셋 구축 대신, **실제 운영 업무 프로세스 자체가 정답 데이터를 축적**하도록 설계되었습니다.

```
인바운드 메일 수신 → 파서 제안 (messages.extraction)
                   ↓
어드민 검토 화면 (ExtractionPanel)에서 PM/운영자가 확인·수정
                   ↓
[제안 확정] 클릭 → messages/{id}.accepted 에 저장 (Ground Truth)
```

- **Ground Truth:** 어드민 화면에서 사람이 검토 후 확정한 `messages/{id}.accepted` 레코드.
- **비교 대상:** 파서가 최초(또는 재파싱 시점)에 도출한 `messages/{id}.extraction`.
- **평가 도구:** `scripts/eval.mjs` (`npm run eval`)
  - Firestore의 `messages` 컬렉션에서 `accepted`가 존재하는 모든 문서를 스캔.
  - 각 메시지별로 `extraction`과 `accepted`를 17대 핵심 필드 단위로 대조하여 지표 산출.

## 3. 지표 정의

평가 지표는 단순 참/거짓을 넘어 프롬프트 개선 방향을 명확히 제시할 수 있도록 3단계로 분류합니다.

| 지표 | 상태 | 정의 | 의미 및 조치 방안 |
|---|---|---|---|
| **일치 (Match)** | 정상 | 정답(`accepted`)의 값과 추출값(`extraction`)이 실질적으로 일치함 (공백, 대소문자, 단위 정규화 후 동등). | 정상 추출. |
| **불일치 (Mismatch)** | 치명적 결함 | 정답에 존재하는 필드를 모델이 **다른 값으로 잘못 추출**함 (예: 수량 오인식, 성분 환각 등). | **가장 위험한 케이스.** 사람이 검토 시 오인을 유발할 수 있으므로 프롬프트 수정 최우선 순위. |
| **미추출 (Not Extracted)** | 누락 | 정답에는 값이 존재하나 모델이 **추출하지 못하고 빈 값(undefined/빈문자열)으로 남김.** | 지어내지 않은 점은 긍정적이나, 프롬프트 지침 보완 또는 필드 인식 컨텍스트 확대 필요. |

### 전체 필드 일치율(%) 산출 공식

$$\text{전체 필드 일치율} = \frac{\sum \text{Match}}{\sum (\text{Match} + \text{Mismatch} + \text{Not Extracted})} \times 100$$

> **참고:** 정답(`accepted`)에 아예 값이 없는 필드는 평가 모수(Denominator)에서 제외(`skip`)합니다. 모델이 없는 것을 채우지 않은 것은 정상 동작이기 때문입니다.

## 4. 사내 어려운 케이스 5선 (The 5 Hard Cases) 분석

실무 수신 메일 중 파서가 취약할 수 있는 5대 극한 케이스를 정의하고 기대 동작을 규정합니다.

### 1) Division Twenty (처방 첨부형 인바운드)
- **상황:** 메일 본문에는 수량(5,000 units), 용량(30ml), 제품명(GHK-Cu Peptide Serum)만 있고, 세부 유효 성분/처방표는 첨부 엑셀 파일(`GHK-Cu_Serum_Spec_v2.xlsx`)에만 존재.
- **위험 요소:** 모델이 GHK-Cu 관련 널리 알려진 화장품 처방 성분(히알루론산, 펩타이드 복합체 등)을 지어내는 환각(Hallucination).
- **기대 동작:**
  - `formula` 객체는 비어있거나, `keyIngredients`는 `undefined`를 반환해야 함.
  - **판정 기준:** 본문에 없는 성분을 단 하나라도 지어내면 프롬프트 즉시 수정 대상(최우선 순위). 없는 걸 비워두는 것이 잘못 채우는 것보다 훨씬 안전함.

### 2) Charity (복수 제품 혼합 문의)
- **상황:** 1통의 메일 내에 남성용 향수(Oud & Bergamot EDP 50ml 3,000개)와 여성용 향수(Rose & Vanilla EDP 50ml 2,000개) 2종이 병렬로 기재됨.
- **위험 요소:** 두 제품을 단일 제품으로 뭉개거나, 수량을 합산(5,000개)해버리는 현상.
- **기대 동작:**
  - `items[]` 배열 길이가 정확히 2여야 함.
  - 각 아이템별로 `productName`, `variantName`, `volume`, `expectedQty`가 명확히 분리 보존되어야 함.

### 3) Nowel (다중 조건/분기형 견적 문의)
- **상황:** 단일 선크림 제품에 대해 용량 및 생산 수량 조건을 두 갈래(Option 1: 50ml / 5,000개 vs Option 2: 100ml / 3,000개)로 타진.
- **위험 요소:** 한쪽 옵션만 임의로 선택해 추출하거나, 용량과 수량을 뒤섞음(50ml 3,000개 등).
- **기대 동작:**
  - `items[]` 배열에 두 옵션이 각각 개별 아이템으로 온전히 보존되어야 함.
  - 공통 성분(Centella Asiatica)과 카테고리(Sunscreen)는 각 항목에 동일하게 반영.

### 4) BHR Skincare (처방 방식 용어 혼동)
- **상황:** 바이어가 커스텀메이드(Custom Formulation, OEM/ODM)와 프라이빗라벨(Private Label, 완제품 용기갈이/OBM) 용어를 혼용하거나 개념을 명확히 구분하지 못함.
- **위험 요소:** 모델이 자의적으로 처방 방식을 단정하여 엉뚱한 공급사 풀을 매칭시킬 위험.
- **기대 동작:**
  - 바이어의 원문 표현을 `formula.notes` 등에 충실히 반영.
  - 모호한 필드에는 낮은 확신도(`confidence: 0.5~0.6`)를 부여하여 어드민 화면에서 사람이 집중 검토할 수 있도록 유도.

### 5) Bala (House of Seoul, 규제 및 배송지 교차)
- **상황:** 인도 배송 목적지 + Rice Ceramide 립 트리트먼트에 SPF 15 자외선 차단 지수 포함.
- **위험 요소:** SPF 표기로 인해 미국 FDA OTC 규제를 필요로 하지 않음에도 임의로 OTC 인증을 요구사항으로 오인하거나, 배송지(인도)와 규제 신호가 어긋남.
- **기대 동작:**
  - `shipping.country: "India"`를 정확히 추출.
  - 자외선 차단 기능 신호(SPF 15)는 제품명/처방에 보존하되, 바이어가 명시하지 않은 불필요한 국가 규제(FDA 등)를 지어내지 않음.

## 5. 코퍼스 편향 안내 (Corpus Bias Warning)

초기 파서 평가를 수행할 때 반드시 염두에 두어야 할 데이터 편향 안내입니다.

> ⚠️ **코퍼스 편향 주의:**
> 1. **바이어 메일 편향:** 현재 구축된 초기 `accepted` 데이터와 수집 메일 코퍼스는 해외 바이어 인바운드(`thomas@medidakoslabs.com` 등) 위주로 집중되어 있습니다.
> 2. **공장 메일 유입 시 문체 격차:** 추후 국내 제조사/공장 담당자 계정(`songjh@`, `kimhs@`, `parkjy@`)이 연동되면 대량의 공장 메일이 유입됩니다.
>    - 공장 메일은 견적서, 부자재 단가표, MOQ 테이블, 감합 테스트 일정, 시험성적서 등 표와 전문 약어가 다수 포함된 완전히 다른 문체를 가집니다.
>    - 따라서 **초기 바이어 메일 기준으로 달성한 80~90%대의 일치율이 공장 메일에서도 동일하게 유지될 것으로 전제해서는 안 됩니다.**
>    - 공장 메일 본격 유입 시 별도의 공장 문체 프롬프트 튜닝 및 필터 분기가 필요할 수 있습니다.

## 7. 향후 평가 및 개선 운영 원칙

1. **프롬프트 수정 전후 필수 실행:**
   ```bash
   npm run eval
   ```
   수정 전 일치율과 수정 후 일치율을 비교하여, 특정 필드를 높이려다 다른 필드의 일치율이 떨어지는 회귀(Regression) 현상이 없는지 확인합니다.
2. **CI / 로컬 테스트 필수 검증:**
   ```bash
   node --loader ./tests/esm-alias-loader.mjs --test tests/parser-replay.test.ts
   npm run typecheck
   ```
   라이브 LLM API를 호출하지 않고도 핵심 3대 케이스 매핑이 깨지지 않는지 상시 검증합니다.
3. **원가/마진 격리 보장:**
   추출 스키마(`extractionSchema`) 및 프롬프트는 절대 제조 원가(`unitCost`), 공급가(`supplierCost`), 마진율 등을 다루지 않으며, 어떠한 경우에도 바이어 클라이언트 응답에 원가 데이터가 노출되지 않도록 서버 사이드 검증을 유지합니다.
