# Channel Talk V2 계획 — 기존 고객 이관·lastContactAt

**상태:** 계획 초안(2026-10-19). 구현 전. 스키마·실행 방식·Secret은 **제안안**이며 승인 전이다.

**브랜치:** `feature/channeltalk-v2`.

**선행 문서:** [V1 설계](2026-10-01-channeltalk-crm-integration.md)의 1장(식별·통합), 4장(프로필 쓰기·타입 검증), 5장(태그·중복), 7장(보류 정책), 8장(스키마), 11·12장. 이 문서에 다시 적지 않은 규칙은 V1 설계를 따른다.

**비공개 자료:** 테스트 제외 정책·ID 목록, 보류 백업은 저장소 밖 비공개 폴더에 있다(권한 600, Git·클라우드 업로드 금지). 이 문서에는 고객 이메일·고객 id·제외 목록을 옮기지 않는다.

## 표기

- **[확정]** 사용자가 결정한 정책(2026-10-12·13).
- **[제안]** Claude가 제안해 함께 검토했으나 구현 승인은 받지 않은 내용. 비공개 정책 문서는 작성만 승인됐다.
- **[미정]** 결정이 필요한 사항. 13장에 모아 둔다.

## 1. 범위

| 포함 | 제외 |
|---|---|
| 기존 고객 이관(OFF 기간 보류 10건 포함) | `ADMIN_EMAILS` 수신자 변경(별도 작업으로 완료) |
| 중복 후보 처리와 검토 목록 | V1 신규 접수 흐름 변경 |
| `lastContactAt` 실시간 갱신과 과거 기록 반영 | 수집기·백오피스·Notion 등 기존 시스템 정리(안정화 뒤 판단) |
| | 수동 병합(C5) |

Landing·Order 실제 접수 검증은 운영 접수가 생길 때 따로 한다. V2 개발의 선행 조건이 아니다.

## 2. 기존 고객 이관

### 확정

- [확정] 대상은 기존 고객 전체와 OFF 기간 보류 10건이다.
- [확정] 같은 고객인지는 안전을 우선해 판단한다. 확실하지 않으면 연결하지 않고 검토로 보낸다.
- [확정] 기존 Channel 프로필은 **빈 칸만** 채운다. 기존 값 덮어쓰기와 자동 병합은 하지 않는다.
- [확정] 이관 전 dry-run을 하고, 명시적 승인을 받은 뒤 실행한다.
- [확정] Firestore 테스트 데이터는 지우지 않고, 이관에서 건너뛴다.

### 제안

- [제안] **매칭 먼저, 생성은 마지막.** Open API에 이메일 검색이 없다. 그래서 Channel 고객 목록이나 Desk 내보내기로 이메일 → 고객 id 표를 만들고 사람이 확인한다. 확인한 표를 `channelTalkIdentities`에 `channelUserOrigin: imported`로 미리 등록한 뒤 이관한다.
- [제안] 수동 등록 고객은 미리 등록하지 않으면 서버 리드가 중복으로 생긴다. 사전 등록을 이관의 필수 단계로 둔다.
- [제안] 이메일이 같아도 고객 유형(`member`)과 통합 상태를 확인한다. 통합 고객은 V1 1장 규칙을 따른다. `unifiedId`는 최대 3단계까지 따라가고, 최종 고객 이메일이 비었거나 같을 때만 그 고객을 쓴다.
- [제안] 기존 회원에게 `PUT` upsert를 보내지 않는다(V1 T8에서 PUT이 기존 값을 지웠다). 쓰기는 `PATCH profileOnce`만 쓰고, `mobileNumber`는 따로 보낸다(V1 4장).
- [제안] 쓰기 값은 V1 4장의 타입 검증과 `marketCountry` 변환표를 그대로 거친다. 담당자 필드와 상담 태그 `응대상태`는 건드리지 않는다.
- [제안] 이관은 상담·내부대화를 만들지 않는다. 고객 프로필 빈 칸 채우기와 매핑 등록만 한다.
- [제안] 실행은 건별로 다시 돌려도 결과가 같게(멱등) 만든다. V1 `channelTalkSync`와 섞지 않도록 별도 처리 경로와 별도 기록을 쓴다.
- [제안] V1이 남긴 `possibleOrphanLead`·`possibleOrphanChat` 기록이 있으면 매칭에서 검토 대상으로 보낸다.

### dry-run 출력 (제안)

- 레코드마다 판정 하나를 낸다: 연결 / 새로 만들기 / 건너뛰기 / 검토. 각 판정에 사유 코드를 붙인다.
- 판정별 건수와 함께 다음을 보고한다.
  - `isTest`로 빠진 건수와 이메일 도메인 분포
  - 예상 밖 404
  - 필드 타입이 틀린 기존 값
  - 예전 키 `companyName`·`country` 값
  - boot null로 지워졌을 수 있는 회원 값
  - 태그 20개 한도에 가까운 고객
- 결과 파일에는 고객 정보가 들어 있다. 저장소가 아닌 비공개 위치에 둔다.

## 3. 중복 처리

- [확정] 중복 후보에는 `dup-candidate` 태그를 붙이고, 별도 검토 목록에 올린다.
- [확정] 판정은 V1 5장을 따른다.
  - `dupPairs`의 상태(`tagged`/`tag_limit`/`dismissed`/`unified`)로 판정한다.
  - Channel이 이미 통합한 쌍은 중복이 아니다.
  - 태그는 최신 태그를 조회한 뒤 합쳐서 `PATCH`한다.
  - 20개 한도에 걸리면 태그를 포기하고 기록만 남긴다.
  - 담당자가 지운 조합에는 다시 붙이지 않는다.
- [확정] 수동 병합(C5)은 하지 않는다.
- [미정] 검토 목록의 저장 위치·관리 방식·담당자. 7장 제안안 참조.

## 4. OFF 기간 보류 10건

- [확정] 보류 10건(`pendingReason: intake_disabled`, `heldReason: pre_activation`)은 실제 고객이다. 테스트 제외 규칙을 적용하지 않고 이관 대상에 넣는다.
- [확정] V1의 `isHeldBeforeActivation`은 그대로 둔다. V1 재시도는 이 기록을 계속 처리하지 않는다.
- [제안] V2는 기존 고객 매칭을 먼저 한 뒤 이 10건을 이관한다. 결과는 V2 처리 기록에 남긴다.
- [미정] 이관 후 V1 `channelTalkSync` 보류 기록에 완료 표시를 할지, 어떤 필드로 할지. 기록 변경은 별도 승인이다.

## 5. 테스트 데이터 제외

- [확정] 테스트 데이터는 보존하고, 제외 목록으로 건너뛴다.
- [제안] 판정 순서는 비공개 정책 문서 2장을 따른다. 위에서부터 먼저 맞는 규칙을 적용한다.
  1. 보호 목록에 있으면 제외하지 않는다.
  2. 정확한 문서 ID가 제외 목록에 있으면 제외한다.
  3. `isTest === true`이면 제외하고, 건수를 보고한다.
  4. 허용 테스트 이메일 형식이거나 제외 목록의 정확한 주소이면 제외한다.
  5. 테스트 Channel id로는 쓰지 않는다.
  6. 근거가 약하면 사람이 검토한다.
- [제안] "test" 문자열이나 내부 도메인만으로는 제외하지 않는다.
- [제안] 제외 목록에 있는(Desk에서 정리된) Channel id의 404는 정상으로 본다. 이 404를 고객 생성이나 매핑 변경의 근거로 쓰지 않는다. 목록에 없는 id의 404는 사람이 검토한다.
- [제안] 백오피스 `threads`·`messages`를 과거 문의 원천으로 쓴다면 제외 ID로 거른다.
- [미정] 제외 ID를 쓰는 방법. 두 가지 중 하나를 고른다.
  - 실행할 때 비공개 파일을 읽는다.
  - 이메일을 뺀 ID 사본을 저장소에 넣는다. 이 경우 별도 승인이 필요하다.

## 6. lastContactAt

### 확정 (2026-10-13)

- **포함**
  - Channel Talk 상담에서 고객과 담당자가 실제로 주고받은 메시지. 고객 메시지와 담당자 응답 모두 반영한다.
  - Channel Talk에 연동된 이메일
- **제외**
  - 내부대화·봇·시스템 로그·팀챗
  - Contact·Landing·Brief·Order 제출 이벤트
  - Channel에 연동되지 않은 별도 Gmail
- 기존 고객은 과거 상담 기록으로 **비어 있을 때만** 채운다. 기존 값은 덮어쓰지 않는다.

### 구현 전 확인 (제안)

- Webhook·OpenAPI로 필요한 메시지와 연동 이메일 이벤트를 받을 수 있는지
- 고객 메시지와 담당자 응답을 구분할 수 있는지. 판정 후보는 `messageCreatedUserChat`의 `personType`, `options`, `log`다.
- 과거 기록을 어디까지 조회할 수 있는지. 문서상 `listUserChats`는 한 번에 최대 30일, `managedAt`은 2026-01-01부터다.
- 중복 이벤트와 재시도를 어떻게 처리할지
- C6(고객 직접 메시지) 테스트 계획. `+chtest` 이메일을 쓰고, 끝나면 제외 목록에 추가한다.

### 설계 방향 (제안)

- 실시간 갱신을 먼저 운영하고, 그다음 과거 기록을 채운다. 반대로 하면 과거 기록을 채운 뒤부터 실시간 수신을 켜기 전까지의 연락이 빠진다.
- 값은 V1 4장 datetime 규칙(분 단위 내림)을 따른다. 분 단위로 비교해 더 최신일 때만 갱신한다.
- 과거 기록은 `profileOnce`로 보내 빈 값만 채운다.
- [미정] 수신 함수 위치, 서명 검증 방식, 이벤트 중복 제거 키
- [미정] Desk `lastContactAt` 필드 생성 시점, Firestore 캐시를 둘지

## 7. 스키마 제안안 (미확정)

스키마 변경이므로 구현 전에 승인받는다. 이름과 필드는 예시다.

| 컬렉션(안) | 용도 | 주요 필드(안) |
|---|---|---|
| `channelTalkMigrationRuns/{runId}` | 실행 단위 기록 | `mode`(`dry_run`/`apply`), 판정별 건수, 시작·종료 시각, 실행자, 입력 목록 버전 |
| `channelTalkMigrationItems/{source}_{docId}` | 건별 이관 기록(멱등 기준) | `decision`(`link`/`create`/`skip`/`review`), `reason` 코드, `channelUserId`, `profileResult`, `status`, `attempts`, `lastError`, `runId` |
| `channelTalkReviews/{id}` | 사람 검토 목록 | `kind`(`dup_candidate`/`unexpected_404`/`weak_test_signal`/`orphan`/…), 관련 이메일 키·Channel id, `state`(`open`/`resolved`/`dismissed`), 처리자·시각 |

- 규칙: 세 컬렉션 모두 `allow read, write: if false`. 서버(Admin SDK)만 접근한다.
- 에뮬레이터 테스트 범위: 클라이언트(로그인·비로그인)의 읽기·쓰기 거부, 기존 규칙 테스트 전부 통과.
- 사유 코드에는 고객 원문이나 개인정보를 넣지 않는다(V1 `identityNote` 원칙).
- 대안: 검토 목록을 Firestore에 두지 않고 Desk 태그와 비공개 보고서만으로 관리할 수 있다. 결정이 필요하다.

## 8. 실행 방식·Secret·환경변수 제안안 (미확정)

| 항목 | 제안 | 대안·고려 |
|---|---|---|
| 이관 실행 위치 | 일회성 함수. Secret Manager 키를 쓰고, 기본값은 dry-run 모드 | 로컬 스크립트는 개인 노트북 자격 증명에 의존하므로 저장소 원칙과 충돌한다 |
| 이관용 Channel 키 | 미정 | 웹 접수 전용 키(`CHANNELTALK_INTAKE_*`)를 재사용 / 이관 전용 키를 새로 발급 |
| Webhook 서명용 Secret | 새 Secret(예: `CHANNELTALK_WEBHOOK_TOKEN`) | Channel 측 서명·토큰 방식을 확인한 뒤 확정 |
| 기능 스위치 | `functions/.env`에 `CHANNELTALK_LAST_CONTACT_ENABLED`(기본 `false`) 등 | V1 `CHANNELTALK_INTAKE_ENABLED`와 같은 방식 |
| Webhook 수신 | 새 HTTP 함수(`asia-northeast3`) | 공개 엔드포인트가 생기므로 이사님과 협의 |
| 호출 속도 | 건당 간격과 1회 처리 상한을 상수로 둔다 | Channel API rate limit 확인 필요 |

새 함수는 기존 함수를 바꾸지 않고 `functions/channeltalk/`에 추가한다. `functions/index.js`에는 내보내는 줄만 추가한다(V1 7장과 같은 방식).

## 9. 테스트 계획

- **단위 테스트(`node --test`)**
  - 이관 판정 함수: 연결·생성·건너뛰기·검토, 제외 판정 순서, 보호 목록 우선, 통합 고객, 404 분기, 보류 10건 포함
  - `profileOnce`만 쓰는지, 기존 회원에 `PUT`이 없는지
  - 타입 검증
  - 태그 병합과 20개 한도
  - lastContactAt 판정: 포함·제외 메시지 유형, 분 단위 비교, 중복 이벤트
- **에뮬레이터:** 새 컬렉션 규칙, 이관 기록의 멱등성(같은 입력을 두 번 실행)
- **운영 검증**(각 단계 별도 승인)
  - dry-run 결과 검토
  - 소수 건으로 먼저 실행
  - 전체 실행
  - 실행 후 비공개 정책 문서 7장 검증: 테스트 ID 쓰기 0건, 보호 목록 미제외, 생성 수가 dry-run과 같은지
- **C6 테스트:** `+chtest` 이메일로 고객 메시지·담당자 응답·내부대화·봇 메시지를 보내 Webhook 판정을 확인한다.

## 10. 배포 계획

1. Firestore rules: 새 컬렉션을 추가할 때만. 파일 전체가 교체되므로 운영 규칙과 저장소 규칙이 같은지 먼저 확인한다. `--dry-run`도 승인 없이 실행하지 않는다.
2. 새 Functions만 선택 배포(`--only functions:<이름>`). 전체 배포와 `notionEmailHistorySync`는 제외한다. 배포는 사용자가 직접 실행한다.
3. Secret 등록, Desk 필드 생성, Webhook 등록은 각 시점에 담당자가 직접 하고 따로 승인한다.
4. 이관 실행(dry-run → 소수 → 전체)과 Webhook 스위치 ON은 각각 승인받는다.

## 11. 구현 순서

1. 문서 정리와 이 계획 승인(현재 단계)
2. 7·8장 결정 → 스키마·rules·테스트 범위 확정
3. 이관 판정 함수 + 단위 테스트, `api.js`에 고객 목록 조회(읽기) 추가
4. dry-run 실행(읽기 전용, 승인) → 매핑표 확정
5. 이관 실행 코드(사전 등록, `profileOnce`, 태그 병합, 멱등 기록) + 에뮬레이터 테스트 → 운영 실행(승인)
6. lastContactAt 사전 확인과 C6 테스트 계획(승인)
7. Webhook 수신 함수(서명 검증, 중복 제거) → 운영 ON(승인)
8. 과거 기록 채우기(빈 값만)
9. 안정화 뒤 수집기 `[TEST]` 상담 처리와 기존 시스템 정리 검토

## 13. 미확정 결정

1. 이관 대상 모집단. 후보는 `users`/`contact`/`landingRequests`/`orders`, 백오피스 `buyers`·`threads`, Channel에만 있는 고객이다. 같은 이메일이 여러 원천에 있을 때 대표 레코드를 고르는 규칙도 정해야 한다.
2. 매핑 원천(Desk 내보내기 / API 목록)과 결과 보관 위치
3. 이관 처리 기록·검토 목록 스키마와 저장 위치(7장)
4. 이관 실행 위치와 사용할 키(8장)
5. 제외 ID를 쓰는 방법(5장)
6. 보류 10건 이관 뒤 V1 기록 표시 여부(4장)
7. 예전 키 `companyName`·`country` 값 처리
8. lastContactAt 수신 함수 위치, 서명 방식, 중복·재시도 처리, 과거 조회 범위, 연동 이메일이 API에 보이는 형태
9. Desk `lastContactAt` 필드 생성 시점, Firestore 캐시 여부
10. 수집기 `[TEST]` 상담 복사 방지 여부
11. 로컬 `.env.local`의 Channel 키가 테스트 키인지 운영 키인지
12. 비공개 자료를 어떻게 인수인계할지. 지금은 한 사람의 노트북에만 있다.
13. Channel 측 문의 사항: 고객이 통합된 뒤 기존 상담이 회원 화면에 나타나지 않는 문제
14. 사람 확인 항목: `sampleRequests` 사용 여부, 테스트 고객 1건의 Desk id 대조(비공개 정책 문서 10장)
