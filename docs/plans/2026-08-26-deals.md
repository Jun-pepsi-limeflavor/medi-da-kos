# 딜 원장과 파이프라인 보드 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** 딜 원장을 만들고, 브랜드 단계를 가로축으로 하는 카드 보드에 공장 단계와 디펜던시 위반을 함께 보인다.

**Architecture:** 브랜드 단계는 딜에 하나, 공장 단계는 제조사마다 하나다. 원가는 서버 전용이므로 딜 문서에 인라인으로 둔다. 디펜던시는 막지 않고 모달로 확인받은 뒤 `events`에 남긴다. 위반 표시는 저장하지 않고 그릴 때 계산한다.

**Spec:** `docs/backoffice-spec.md` — 4.1, 4.3, 4.4, 7장 2·3·4

**선행:** 계획 2 (원장) 머지

**밀도 안내:** 스키마와 단계 전환 로직은 코드까지, 화면은 구조까지 쓴다. 칸반은 `src/components/crm/CrmKanbanBoard.tsx` 프로토타입을 고쳐 쓰는데, 그 파일이 미추적이라 실제 내용을 열어보고 맞춰야 한다.

### Task 1: 단계 로직 — 순수 함수로 먼저

**여기부터 하는 이유:** 이 계획에서 유일하게 틀리기 쉬운 부분이고, Firestore도 화면도 없이 전부 테스트된다.

**Interfaces**

  - `DEPENDENCIES: { prereq, dependent }[]` (5개)
  - `findViolations(deal): Violation[]`
  - `checkGate(deal, target): GateResult` — `{ ok: true } | { ok: false, reason: string }`
  - `effectiveFactoryStage(deal): number | null`

- [ ] **Step 1: 테스트 먼저**

`tests/stages.test.ts`에서 검증할 것:

**`effectiveFactoryStage`** — 카드에 뭘 보일지 정한다
- 확정(`fix`) 제조사가 있으면 그 단계
- 확정이 없으면 진행중(`ing`) 중 **가장 앞선** 단계
- 기각(`drop`)은 세지 않는다

**`findViolations`** — 스펙 4.4의 표 5줄이 그대로 케이스가 된다

- **제조사 중 하나라도** 공장2 이상이면 위반 아님
- 공장3(샘플 요청)인데 브랜드3 미만 → 위반
- 공장4(샘플 수정)인데 브랜드5(피드백) 미만 → 위반
- 공장5(계약)인데 브랜드7(결제/발주) 미만 → 위반
- 공장1(견적 문의)인데 브랜드1(접수) 미만 → 위반
- 정상 진행 → 빈 배열

**`checkGate`** — 차단 셋
- 브랜드4로 갈 때 마지막 `samples[]` 회차에 `trackingNumber`가 없으면 거부

### Task 3: 단계 전환 라우트 — 게이트가 여기 있다

**이 계획에서 가장 중요한 파일이다.**

- [ ] **Step 1: 계약**

```
POST /api/admin/deals/{id}/stage
{ track: "brand" | "factory", supplierId?: string, target: number, override?: boolean }
```

`track: "factory"`면 `supplierId`가 필수다. 공장 단계는 제조사마다 있기 때문이다.

- [ ] **Step 2: 처리 순서**

```
1. checkGate(deal, target)          실패 → 409, override 로도 못 넘는다
2. findViolations(가상의 다음 상태)  있으면
     override !== true              → 200 + { needsConfirm: true, violations }
     override === true              → 진행
3. 단계 갱신
4. events 기록 — type: "stage", override 였으면 "override" + reason
```

**2번이 200을 주는 게 핵심이다.** 오류가 아니라 "확인이 필요하다"는 답이다. 화면이 모달을 띄우고 사람이 누르면 `override: true`로 같은 요청을 다시 보낸다.

**1번은 `override`로 못 넘는다.** 디펜던시와 게이트의 차이가 여기서 코드로 나타난다 — 순서가 뒤집히는 건 현실이고, 송장 없이 발송 처리하는 건 사고다.

- [ ] **Step 3: 테스트**

라우트 테스트는 Firestore가 필요해 무겁다. **게이트·디펜던시 판정은 Task 1에서 이미 순수 함수로 검증됐다.** 여기서는 배선만 확인한다 — 게이트 실패가 409인지, 위반이 200+`needsConfirm`인지, `override`가 통과하는지.

- [ ] **Step 4: 브라우저 확인**

| 시나리오 | 기대 |
|---|---|
| 견적 회신한 공장 없이 샘플 발주로 | 모달 → 확인 누르면 넘어감 |
| 그 뒤 `events` 확인 | `type: "override"`, `actor`에 내 이메일, `reason` |
| 송장 없이 샘플 발송으로 | **차단.** 모달 없음 |
| 마지막 회차에 송장 넣고 다시 | 통과 |
| 2차 샘플 회차 추가 후 송장 없이 발송 | **차단** (1차 송장이 있어도) |

마지막 줄이 "마지막 회차 기준"을 실제로 확인하는 지점이다.

### Task 4: 보드와 상세 화면


`CrmStage`가 단일 8단계(`inquiry`…`shipping`)로 돼 있다. **컴포넌트는 살리고 타입만 갈아끼운다** (스펙 4.4).

- [ ] **Step 2: 카드 한 장에 들어갈 것**

```
┌──────────────────────────────┐
│ Charity — TJ perfumes        │
│ 향수 30ml × 2종 · 5,000개     │
│                              │
│ 공장  샘플 요청 (그린코스)     │ ← 위반이면 색이 다르다
│ 샘플 발송 (3차)               │ ← 4차 이상이면 색이 다르다
│ 📎 2   💬 7                   │
└──────────────────────────────┘
```

- 가로축은 **브랜드 단계 8개**
- 공장 단계는 `effectiveFactoryStage()` — 확정 제조사가 있으면 그것, 없으면 진행중 중 최선두
- 위반은 `findViolations()`로 **그릴 때 계산한다.** 저장하지 않는다 (스펙 4.4)
- 샘플 회차는 `samples.length`

- [ ] **Step 3: 상세 화면**

PRD ①~⑨ 탭 + 제조사 비교 표 + `events` 타임라인 + 연결된 스레드.

제조사 비교 표에 `unitCost`·`moq`·`leadTime`이 나란히 보인다. **이 화면이 원가를 다루는 유일한 곳이다.**

- [ ] **Step 4: 제조사 뷰에 딜 붙이기**

계획 2의 `/admin/suppliers`에 "이 공장이 물고 있는 딜"을 더한다. `supplierIds` 배열에 `array-contains` 조회다 (스펙 4.1). 진행중·확정·기각으로 갈라 보인다.

- [ ] **Step 5: 확인**

| 확인 | 기대 |
|---|---|
| 딜을 손으로 하나 만든다 | 보드에 카드가 뜬다 |
| 제조사 둘을 붙이고 단계를 다르게 | 카드엔 앞선 쪽이 뜬다 |
