# 딜 원장과 파이프라인 보드 계획

> **For agentic workers:** Steps use checkbox (`- [ ]`) syntax.

**Goal:** 다제품·다공급자 딜 원장을 만들고, 브랜드 단계·공장 단계·다음 작업·샘플 QC·구간별 배송을 한 보드와 상세 화면에서 운영한다.

**Architecture:** 브랜드 단계는 딜에 하나, 공장 단계는 `supplierEngagements`마다 하나다. 제품·공급자 관계·샘플 회차·배송 구간·작업을 독립 서브컬렉션으로 두고 안정적인 ID로 연결한다. 원가·환율·마진은 `private/finance`와 전용 서버 저장소에만 둔다. engagement와 `supplierIds`, 단계 전환과 배송 연계·이벤트처럼 한 명령에서 함께 바뀌는 값은 각각 하나의 Firestore transaction으로 저장한다.

**Spec:** `docs/backoffice-spec.md` — 4.1, 4.3, 4.4, 7장 2·3·4

**선행:** 계획 2 (원장) 머지

**밀도 안내:** 스키마와 단계 전환 로직은 코드까지, 화면은 구조까지 쓴다. 칸반은 `src/components/crm/CrmKanbanBoard.tsx` 프로토타입을 고쳐 쓰는데, 그 파일이 미추적이라 실제 내용을 열어보고 맞춰야 한다.

### Task 1: 단계 로직 — 순수 함수로 먼저

**여기부터 하는 이유:** 이 계획에서 유일하게 틀리기 쉬운 부분이고, Firestore도 화면도 없이 전부 테스트된다.

**Interfaces**

- Produces:
  - `BRAND_STAGES` (8), `FACTORY_STAGES` (9)
  - `DEPENDENCIES: { prereq, dependent }[]` (5개)
  - `findViolations(deal): Violation[]`
  - `checkGate(snapshot, transition): GateResult` — `{ ok: true } | { ok: false, reason: string }`
  - `effectiveFactoryStage(engagements): number | null`

- [ ] **Step 1: 테스트 먼저**

`tests/stages.test.ts`에서 검증할 것:

**`effectiveFactoryStage`** — 카드에 뭘 보일지 정한다

- 확정(`fix`) 제조사가 있으면 그 단계
- 확정이 없으면 진행중(`ing`) 중 **가장 앞선** 단계
- 기각(`drop`)은 세지 않는다
- 제조사가 하나도 없으면 `null`

**`findViolations`** — 스펙 4.4의 표 5줄이 그대로 케이스가 된다

- 브랜드3(샘플 발주)인데 공장2(견적 회신)에 도달한 제조사가 없다 → 위반
- **제조사 중 하나라도** 공장2 이상이면 위반 아님
- 공장3(샘플 요청)인데 브랜드3 미만 → 위반
- 공장4(샘플 수정)인데 브랜드5(피드백) 미만 → 위반
- 공장5(계약)인데 브랜드7(결제/발주) 미만 → 위반
- 공장1(견적 문의)인데 브랜드1(접수) 미만 → 위반
- 정상 진행 → 빈 배열

**`checkGate`** — 차단 셋

- 브랜드4로 갈 때 해당 제품의 가장 큰 `roundNo`를 가진 활성 `sampleRound`가 없으면 거부
- HQ 경유 샘플은 `receivedAt`·`qcStatus='passed'`·`hq_to_buyer` 송장이 모두 있어야 통과
- 공장 직송 샘플은 `qcStatus='waived'`·공백 아닌 `qcWaiverReason`·`supplier_to_buyer` 송장이 모두 있어야 통과
- 다른 제품이나 이전 `roundNo`의 송장은 현재 회차를 통과시키지 않는다
- 배송지가 브라질인데 `shippingInfo.taxId`가 없으면 브랜드4 거부
- 브라질이 아니면 `taxId` 없어도 통과
- 브랜드8로 갈 때 `kind='main'`인 shipment의 `trackingNumber`가 없으면 거부. route는 세 값 중 어느 것이어도 된다
- 공장7로 갈 때 `escrowStatus !== "funded"`면 거부
- 그 외 전환은 전부 통과 (디펜던시는 게이트가 아니다)

**본품 동기화**

- 동일한 `kind='main'`, `route='supplier_to_buyer'` shipment를 가리킬 때만 공장9와 브랜드8을 같이 전환
- HQ 경유이면 `supplier_to_hq`와 `hq_to_buyer`가 다른 shipment이므로 자동 동기화하지 않음

### Task 2: 딜 스키마와 저장소

**Interfaces**

- Produces:

- [ ] **Step 1: 스키마**

PRD ①~⑨ ⑪을 스펙 4.1의 core와 서브컬렉션으로 나눈다. 딜 생성 입력에는 `intakeReviewId`, `buyerId`, `reference`, `buyerInfo`, `certifications`, `timeline`, `shippingInfo`, `additionalRequests`가 들어간다. `escrowStatus`는 본주문 0건이므로 선택이다.

운영 스키마의 최소 계약:

```typescript
dealItemSchema = {
  productType, variantName, volume, quantity,
  formulaSpec, packagingSpec,
}

supplierEngagementSchema = {
  supplierId,
  roles: ("formulation"|"packaging"|"filling"|"testing"|"logistics")[],
  supplyMode: "turnkey"|"buyer_supplied"|"kta_supplied",
  contactStatus: "ing"|"fix"|"drop",
  stageFactory: 1..9,
  contactPersonSnapshot,
  moq?, leadTime?, supportedCerts?, notes?, ipTerms?,
}

sampleRoundSchema = {
  itemId, supplierId, roundNo,
  producedQty?, retainedQty?, receivedAt?,
  qcStatus: "pending"|"passed"|"failed"|"waived",
  qcNotes?, qcWaiverReason?, verdict?, feedbackAt?, feedbackNotes?,
}

shipmentSchema = {
  kind: "sample"|"main",
  route: "supplier_to_hq"|"hq_to_buyer"|"supplier_to_buyer",
  sampleRoundId?, trackingNumber?, carrier?, status?,
  shippedAt?, deliveredAt?, addressSnapshot, customsSnapshot,
}

  type, summary, ownerId,
  waitingOn: "us"|"buyer"|"supplier"|"carrier",
```

`roundNo`는 같은 `itemId` 안에서 1부터 증가하고 중복을 트랜잭션으로 거부한다. `producedQty`와 `retainedQty`가 모두 있으면 `retainedQty <= producedQty`여야 한다. `qcStatus='waived'`이면 사유가 필수다.

- [ ] **Step 5: 운영 서브컬렉션 저장 계약을 구현한다**

### Task 3: 단계 전환 라우트 — 게이트가 여기 있다

**이 계획에서 가장 중요한 파일이다.**

- [ ] **Step 1: 계약**

```
POST /api/admin/deals/{id}/stage
{
  track: "brand" | "factory",
  engagementId?: string,
  target: number,
  override?: boolean,
  reason?: string,
  shipmentId?: string,
  itemId?: string
}
```

`track: "factory"`면 `engagementId`가 필수다. 같은 제조사가 제형과 패키징 역할로 두 번 참여할 수 있어 `supplierId`만으로는 대상을 고를 수 없다. `override=true`면 공백이 아닌 `reason`이 필수다.

- [ ] **Step 2: 처리 순서**

```
1. transaction 안에서 deal·engagement·최신 sampleRound·shipments를 다시 읽음
2. checkGate(snapshot, transition)   실패 → 409, override 로도 못 넘는다
3. findViolations(가상의 다음 상태)  있으면
     override !== true               → transaction 종료, 200 + { needsConfirm: true, violations }
     override === true               → reason 검증 후 진행
4. 단계·shipment 연계를 갱신
5. 공장9이고 같은 main shipment가 supplier_to_buyer이면 브랜드8도 갱신
6. events 기록 — type: "stage", override 였으면 "override" + reason
7. transaction commit
```

**2번이 200을 주는 게 핵심이다.** 오류가 아니라 "확인이 필요하다"는 답이다. 화면이 모달을 띄우고 사람이 누르면 `override: true`로 같은 요청을 다시 보낸다.

**1번은 `override`로 못 넘는다.** 디펜던시와 게이트의 차이가 여기서 코드로 나타난다 — 순서가 뒤집히는 건 현실이고, 송장 없이 발송 처리하는 건 사고다.

- [ ] **Step 3: 테스트**

에뮬레이터 route 테스트에서 게이트 실패가 409인지, 위반이 200+`needsConfirm`인지, 사유 없는 override가 400인지, 성공 시 단계와 event가 함께 생기는지 확인한다. event 쓰기를 강제로 실패시킨 픽스처에서는 단계도 바뀌지 않아야 한다.

- [ ] **Step 4: 브라우저 확인**

| 시나리오                                 | 기대                                                    |
| ---------------------------------------- | ------------------------------------------------------- |
| 견적 회신한 공장 없이 샘플 발주로        | 모달 → 확인 누르면 넘어감                              |
| 그 뒤`events` 확인                     | `type: "override"`, `actor`에 내 이메일, `reason` |
| 송장 없이 샘플 발송으로                  | **차단.** 모달 없음                               |
| HQ 입고·QC 통과 후 HQ→바이어 송장 입력 | 통과                                                    |
| 직송인데 QC 면제 사유 없음               | **차단**                                          |
| 2차 sampleRound 추가 후 1차 송장만 있음  | **차단**                                          |
| 공장9 + main 직송 shipment               | 같은 transaction에서 브랜드8도 전환                     |
| 공장9 + supplier→HQ shipment            | 브랜드8은 그대로                                        |

마지막 줄이 "마지막 회차 기준"을 실제로 확인하는 지점이다.

```typescript
export function normalizeBriefForStorage(brief: CMBrief): CMBrief {
  const normalized = structuredClone(brief);
  if (normalized.step4?.orderQuantityTbd) {
    delete normalized.step4.orderQuantity;
    delete normalized.step4.moq;
  }
  return normalized;
}
```
