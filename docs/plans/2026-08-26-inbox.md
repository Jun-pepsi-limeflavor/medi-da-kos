# 통합 받은편지함 계획

> **For agentic workers:** Steps use checkbox (`- [ ]`) syntax.

**Goal:** 수집된 메시지를 노션 inbox 형태로 한 화면에 모으고, 발신자를 바이어·제조사에 연결한다.

**Architecture:** `messages`는 제공자 원문과 파싱 상태, `threads`는 읽음·보관·연결·side처럼 사람이 바꾸는 상태를 맡는다. 계획 3의 수집기가 두 문서를 트랜잭션으로 갱신하므로 목록은 `threads`를 읽고 상세만 `threadKey`의 메시지를 읽는다. 재수집은 사람 상태를 덮지 않는다.

**Spec:** `docs/backoffice-spec.md` — 6.2, 7장 1·5

**선행:** 계획 3 (수집기 관통) 머지. **`docs/gmail-response-shape.md`를 먼저 읽는다** — 실제 필드 이름이 거기 있다.

**밀도 안내:** 이 계획은 코드 블록이 적다. 화면 마크업은 계획 2의 `suppliers/page.tsx`·`SupplierForm.tsx` 골격을 그대로 따르고, 데이터 모양은 계획 3이 실제로 적재한 문서를 보고 맞춘다. 지어낸 필드로 코드를 쓰지 않는다.

## Global Constraints

계획 1·2를 상속한다. 추가로:

- 메시지 본문에는 **바이어 실명·주소가 들어 있다.** 로그에 본문을 찍지 않는다
- 첨부는 **Cloud Storage에 복사하지 않는다.** 라우트가 provider에서 스트림한다
- `messages`의 제공자 원문을 UI 액션으로 수정하지 않는다
- `threads.sideSource='manual'`은 수집기나 주소 자동 매칭이 덮지 않는다
- `threadKey`는 `{channel}:{sourceAccount}:{providerThreadId}`다

### Task 1: 메시지·스레드 스키마와 저장소

**Interfaces**

- Produces:
  - `type Message`, `type Thread`
  - `listThreads(filters, limit)`, `getThread(threadKey)`, `listThreadMessages(threadKey)`
  - `setThreadState(threadKey, patch, actor)`, `linkThread(threadKey, link, actor)`, `correctThreadSide(threadKey, side, actor)`

- [ ] **Step 1: 계획 3이 실제로 쓴 문서를 먼저 본다**

Firebase 콘솔에서 `messages` 문서 하나를 열어 필드를 그대로 받아 적는다. 계획 3의 `normalizeMessage()`가 만든 모양이 기준이고, 이 스키마는 **그걸 따라간다.** 반대가 아니다.

- [ ] **Step 2: 상태 경계 테스트 먼저**

`tests/thread-state.test.ts` — Zod와 순수 파생 함수만 검사한다.

검증할 것:

- `readState`, `triageState`, `linkState`, `side`는 서로 독립적으로 검증된다
- `lastDirection: "in"`이면 `needsReply`가 참이고 `out`이면 거짓이다
- `side='unknown'`이 정상 값이다
- `sideSource='manual'`이면 자동 판정 결과를 적용하지 않는다
- `correctThreadSide()`는 공백 아닌 사유를 요구하고 `sideHistory[]`에 from·to·reason·actor·at을 append한다
- 다른 계정의 같은 `providerThreadId`가 다른 `threadKey`를 만든다

`needsReply`가 이 화면의 존재 이유다. 스펙 1장의 *"답장 안 한 것을 드러낸다"*가 이 한 줄이다.

- [ ] **Step 3: 스키마와 파생 함수 구현 → 통과 확인**
- [ ] **Step 4: 저장소 작성**

`listThreads()`는 `orderBy("lastMessageAt", "desc").limit(n)`이다. 기본 300개로 시작하고 URL 필터는 읽은 뒤 메모리에서 적용한다. `listThreadMessages()`는 `where("threadKey", "==", threadKey).orderBy("sentAt")`다.

```
ponytail: 스레드 300개를 읽어 필터한다. 지금 규모에 필터 조합별 복합 인덱스를 만들지 않는다.
          오래된 스레드에 새 메시지가 오면 lastMessageAt 이 갱신돼 목록에 다시 뜬다.
```

상태 API는 허용 필드만 받는다.

```typescript
const threadStatePatchSchema = z.object({
  readState: z.enum(["unread", "read"]).optional(),
  triageState: z.enum(["open", "archived", "ignored"]).optional(),
}).refine((v) => Object.keys(v).length > 0);
```

### Task 2: 받은편지함 화면

**Interfaces**

- Consumes: Task 1 전부

- [ ] **Step 1: 목록 페이지**

계획 2의 `suppliers/page.tsx` 골격을 따른다. `export const dynamic = "force-dynamic"`를 잊지 않는다.

한 줄에 보일 것:

```
● Charity (Candy Kobia)          brand   gmail_thomas    📎        2시간 전
  Perfume sample request — 남녀 2종 30ml straight-sided…
```

- 안 읽음(`readState: "unread"`)은 굵게 + 좌측 점
- `needsReply`인 스레드는 좌측 점을 다른 색으로
- `side` 배지 (`brand` / `factory` / `unknown`). `unknown`은 판정 필요 색상
- 첨부가 있으면 📎 — `messages[].attachments.length`로 계산, 새 필드 없음

- [ ] **Step 2: 필터**

`readState` · `triageState` · `linkState` · `side` · `channel` · `needsReply` 여섯. URL 쿼리스트링으로 받는다 — 서버 컴포넌트가 읽고, 필터 건 화면을 링크로 공유할 수 있다.

- [ ] **Step 3: 스레드 상세**

메시지를 시간순으로 쌓고, 각 메시지에 발신자·시각·본문·첨부를 보인다. 본문은 `whitespace-pre-wrap`으로 그대로 보인다 — 메일 본문에 서식을 입히면 원문이 왜곡된다.

- [ ] **Step 4: 처리 액션**

`[보관]` `[읽음]` `[바이어 연결]` `[제조사 연결]` `[side 정정]`. 처리해도 데이터가 사라지지 않고 필터로 갈린다. 보관은 `triageState='archived'`, 읽음은 `readState='read'`라 서로 덮지 않는다.

- [ ] **Step 5: 브라우저 확인**

| 확인                        | 기대                                     |
| --------------------------- | ---------------------------------------- |
| 실제 수집된 스레드가 보인다 | 계획 3이 넣은 문서                       |
| 마지막이 받은 메일인 스레드 | `needsReply` 표시                      |
| 보관 후 목록                | 기본 필터에서 빠지고`보관` 필터에 있다 |
| 새로고침                    | 상태가 유지된다 (Firestore에 갔다)       |

### Task 3: 발신자 판정·자동 연결·메일 인테이크

**Interfaces**

- Consumes: `findBuyerByEmail()`, `findSupplierByEmail()`, `setIntakeReview()` (계획 2)

- [ ] **Step 1: 연결 규칙**

```
side = "brand"    → buyers.emails[] 에서 array-contains 조회
side = "factory"  → suppliers.contactEmails[] 에서 array-contains 조회
side = "unknown"  → 양쪽을 조회하되 자동 연결하지 않고 후보를 표시
```

인바운드는 `from`, 아웃바운드는 우리 주소를 제외한 `to[]`를 상대 주소로 쓴다. 메일함 기본 side와 반대쪽에서만 정확히 하나가 매칭되면 `sideSource='address_match'`로 고친다. 양쪽 모두 또는 어느 쪽에도 매칭되지 않으면 `unknown`을 유지한다. `sideSource='manual'`은 절대 자동 변경하지 않는다.

- [ ] **Step 2: 못 찾으면 후보로 남긴다**

자동 생성하지 않는다. 상세 화면에 `[이 주소로 바이어 만들기]` 버튼을 두고 사람이 누른다. 계획 2의 폼을 이메일이 채워진 채로 연다.

- [ ] **Step 3: 연결 결과를 스레드에 쓴다**

`threads/{threadKey}`에 `buyerId` 또는 `supplierId`, `linkState='linked'`, `linkedBy`, `linkedAt`을 쓴다. 원문 메시지는 수정하지 않는다.

- [ ] **Step 4: 메일 기반 raw 인테이크를 만든다**

처음 연 외부 스레드에 `intakeReviews`가 없으면 다음 결정적 판정을 만든다.

```typescript
{
  source: "message",
  externalId: threadKey,
  sourceRef: `threads/${threadKey}`,
  status: "raw",
  reason: "",
  isTest: false,
  isTestReason: "",
}
```

자동으로 `qualified`로 올리거나 딜을 만들지 않는다. `[정상 리드로 승인]`은 계획 2의 인테이크 판정 API를 사용한다.

- [ ] **Step 5: 확인**

볼트에 있는 실제 주소로 바이어를 하나 만들고, 그 사람 메일이 자동 연결되는지 본다.

### Task 4: 첨부 다운로드

- [ ] **Step 1: 프록시 라우트**

`GET /api/admin/messages/[id]/attachments/[attId]` → `withAdmin` → Gmail `attachments.get` → base64url 디코드 → 스트림

`Content-Disposition: attachment; filename="…"`을 붙인다. 파일명에 한글이 오면 `filename*=UTF-8''` 형식이 필요하다.

- [ ] **Step 2: Division Twenty 건으로 확인**

**볼트 기준 실제 케이스다** — 본문이 아니라 첨부 xlsx에 처방이 들어 있다. 이게 열려야 v1에서 첨부 파싱을 뺀 결정이 성립한다.

### Task 5: 설정 → 메일 제공자

- [ ] **Step 1: 화면**

```
/admin/settings/mail-providers

thomas@medidakoslabs.com   ● 연결됨   마지막 성공 2분 전   127통   [진단]
hally@medidakoslabs.com    ● 오류     unauthorized_client       [진단]
songjh@techasset.co.kr     ● 연결됨   정상 0건                   [진단]
```

`ingestState/{account}`의 `lastSuccessAt`·`lastError`·`processedCount`로 만든다. `processedCount=0`이고 `lastError=null`인 **정상 0건**과 오류를 다른 상태로 표시한다.

- [ ] **Step 2: 재연결 버튼**

도메인 전체 위임 방식에서는 재연결이 **토큰 재발급이 아니라 진단**이다. 버튼을 누르면 그 메일함으로 토큰을 한 번 받아보고 결과를 보인다.

```
✅ thomas@ 접근 가능
❌ hally@ — unauthorized_client. 관리콘솔 위임 등록을 확인하세요
```

**스펙 6.4의 "토큰 재발급 버튼"이 이 형태가 되는 이유** — 위임 방식엔 사용자가 다시 로그인할 대상이 없다. 진단이 그 자리를 대신한다. Outlook과 채널톡은 계획 7에서 붙고, 그쪽은 진짜 재발급이 필요할 수 있다.

- [ ] **Step 3: 확인 후 PR**
