# 통합 받은편지함 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** 수집된 메시지를 노션 inbox 형태로 한 화면에 모으고, 발신자를 바이어·제조사에 연결한다.

**Architecture:** 스레드 단위로 묶어 보여주되 저장은 메시지 단위 그대로다. 묶기는 **읽을 때 메모리에서** 한다 — Firestore에 그룹 기능이 없고, 665통 규모에서 스레드 컬렉션을 따로 유지하면 두 곳이 어긋날 여지만 생긴다.

**Spec:** `docs/backoffice-spec.md` — 6.2, 7장 1·5

**선행:** 계획 3 (수집기 관통) 머지. **`docs/gmail-response-shape.md`를 먼저 읽는다** — 실제 필드 이름이 거기 있다.

**밀도 안내:** 이 계획은 코드 블록이 적다. 화면 마크업은 계획 2의 `suppliers/page.tsx`·`SupplierForm.tsx` 골격을 그대로 따르고, 데이터 모양은 계획 3이 실제로 적재한 문서를 보고 맞춘다. 지어낸 필드로 코드를 쓰지 않는다.

---

## Global Constraints

계획 1·2를 상속한다. 추가로:

- 메시지 본문에는 **바이어 실명·주소가 들어 있다.** 로그에 본문을 찍지 않는다
- 첨부는 **Cloud Storage에 복사하지 않는다.** 라우트가 provider에서 스트림한다
- 스레드 묶기를 위해 `threads` 컬렉션을 만들지 않는다

```bash
git switch -c feat/inbox origin/dev
```

### Task 1: 메시지 스키마와 저장소

**Interfaces**
- Produces: `type Message`, `listRecentMessages(limit)`, `groupIntoThreads(messages)`, `getThread(threadId)`, `setMessageStatus(id, status, actor)`

- [ ] **Step 1: 계획 3이 실제로 쓴 문서를 먼저 본다**

Firebase 콘솔에서 `messages` 문서 하나를 열어 필드를 그대로 받아 적는다. 계획 3의 `normalizeMessage()`가 만든 모양이 기준이고, 이 스키마는 **그걸 따라간다.** 반대가 아니다.

- [ ] **Step 2: 스레드 묶기 테스트 먼저**

`tests/thread-grouping.test.ts` — 순수 함수라 Firestore 없이 테스트된다.

검증할 것:
- 같은 `threadId`가 하나로 묶인다
- 스레드의 `lastAt`은 가장 늦은 메시지의 `sentAt`이다
- **마지막 메시지가 `direction: "in"`이면 `needsReply`가 참이다**
- 마지막이 `out`이면 거짓이다
- 스레드 정렬은 `lastAt` 내림차순이다
- 스레드의 `side`는 구성 메시지의 `side`다 (섞이면 첫 메시지 기준)

`needsReply`가 이 화면의 존재 이유다. 스펙 1장의 *"답장 안 한 것을 드러낸다"*가 이 한 줄이다.

- [ ] **Step 3: `groupIntoThreads()` 구현 → 통과 확인 → 커밋**

- [ ] **Step 4: 저장소 작성**

`listRecentMessages()`는 `orderBy("sentAt", "desc").limit(n)`이다. 기본 300통으로 시작한다.

```
ponytail: 최근 300통만 읽어 메모리에서 묶는다. 전수 스캔이 아니라 오래된 스레드에
          새 메시지가 오면 목록에 다시 뜨는 구조다. 이게 원하는 동작이기도 하다.
          수만 통이 되면 스레드 요약 컬렉션으로 뺀다.
```

### Task 2: 받은편지함 화면

**Interfaces**
- Consumes: Task 1 전부

- [ ] **Step 1: 목록 페이지**

계획 2의 `suppliers/page.tsx` 골격을 따른다. `export const dynamic = "force-dynamic"`를 잊지 않는다.

한 줄에 보일 것:

```
● Charity (Candy Kobia)          brand   gmail_thomas    📎        2시간 전
  Perfume sample request — 남녀 2종 30ml straight-sided…
```

- 안 읽음(`status: "new"`)은 굵게 + 좌측 점
- `needsReply`인 스레드는 좌측 점을 다른 색으로
- `side` 배지 (`brand` / `factory`)
- 첨부가 있으면 📎 — `messages[].attachments.length`로 계산, 새 필드 없음

- [ ] **Step 2: 필터**

`status` · `side` · `channel` · `needsReply` 넷. URL 쿼리스트링으로 받는다 — 서버 컴포넌트가 읽고, 상태를 클라이언트에 둘 이유가 없고, 필터 건 화면을 링크로 공유할 수 있다.

- [ ] **Step 3: 스레드 상세**

메시지를 시간순으로 쌓고, 각 메시지에 발신자·시각·본문·첨부를 보인다. 본문은 `whitespace-pre-wrap`으로 그대로 보인다 — 메일 본문에 서식을 입히면 원문이 왜곡된다.

- [ ] **Step 4: 처리 액션**

`[보관]` `[읽음]` `[바이어 연결]` `[제조사 연결]`. 처리해도 목록에서 사라지지 않고 필터로 갈린다 — 노션 inbox가 그렇다.

- [ ] **Step 5: 브라우저 확인**

| 확인 | 기대 |
|---|---|
| 실제 수집된 스레드가 보인다 | 계획 3이 넣은 문서 |
| 마지막이 받은 메일인 스레드 | `needsReply` 표시 |
| 보관 후 목록 | 기본 필터에서 빠지고 `보관` 필터에 있다 |
| 새로고침 | 상태가 유지된다 (Firestore에 갔다) |

### Task 3: 발신자 자동 연결

**Interfaces**
- Consumes: `findBuyerByEmail()` (계획 2), `findSupplierByName()` (계획 2)

- [ ] **Step 1: 연결 규칙**

```
side = "brand"    → buyers.emails[] 에서 array-contains 조회
side = "factory"  → suppliers.email 로 조회
```

**메일함이 딜의 양면과 일치한다는 사실이 여기서 값을 낸다** (스펙 4.2). 어느 원장을 뒤질지 판정할 필요가 없다.

- [ ] **Step 2: 못 찾으면 후보로 남긴다**

자동 생성하지 않는다. 상세 화면에 `[이 주소로 바이어 만들기]` 버튼을 두고 사람이 누른다. 계획 2의 폼을 이메일이 채워진 채로 연다.

- [ ] **Step 3: 연결 결과를 메시지에 쓴다**

`buyerId` 또는 `supplierId`. **스레드의 모든 메시지에 같이 쓴다** — 한 스레드는 한 상대와의 대화다.

- [ ] **Step 4: 확인**

볼트에 있는 실제 주소로 바이어를 하나 만들고, 그 사람 메일이 자동 연결되는지 본다.

### Task 4: 첨부 다운로드

- [ ] **Step 1: 프록시 라우트**

`GET /api/admin/messages/[id]/attachments/[attId]` → `withAdmin` → Gmail `attachments.get` → base64url 디코드 → 스트림

`Content-Disposition: attachment; filename="…"`을 붙인다. 파일명에 한글이 오면 `filename*=UTF-8''` 형식이 필요하다.

- [ ] **Step 2: Division Twenty 건으로 확인**

**볼트 기준 실제 케이스다** — 본문이 아니라 첨부 xlsx에 처방이 들어 있다. 이게 열려야 v1에서 첨부 파싱을 뺀 결정이 성립한다.

### Task 5: 설정 → 메일 제공자

- [ ] **Step 1: 화면**

```
/admin/settings/mail-providers

thomas@medidakoslabs.com   ● 연결됨   마지막 수집 2분 전   127통   [재연결]
hally@medidakoslabs.com    ○ 미연결                              [연결]
```

`ingestState/{account}`의 `lastEpochSeconds`와 `messages`의 계정별 개수로 만든다.

- [ ] **Step 2: 재연결 버튼**

도메인 전체 위임 방식에서는 재연결이 **토큰 재발급이 아니라 진단**이다. 버튼을 누르면 그 메일함으로 토큰을 한 번 받아보고 결과를 보인다.

```
✅ thomas@ 접근 가능
❌ hally@ — unauthorized_client. 관리콘솔 위임 등록을 확인하세요
```

**스펙 6.4의 "토큰 재발급 버튼"이 이 형태가 되는 이유** — 위임 방식엔 사용자가 다시 로그인할 대상이 없다. 진단이 그 자리를 대신한다. Outlook과 채널톡은 계획 7에서 붙고, 그쪽은 진짜 재발급이 필요할 수 있다.

- [ ] **Step 3: 확인 후 PR**

```bash
gh pr create --base dev --title "feat(admin): 통합 받은편지함과 메일 제공자 설정"
```
