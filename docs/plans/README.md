## 밀도가 다른 이유

계획 1이 코드 블록까지 정확한 건 참조하는 심볼을 전부 실제 코드에서 확인했기 때문이다 — `getFirebaseAuth()`가 `src/lib/firebase.ts:42`에 있는 것, `@/*` alias가 tsconfig에 있는 것, `server-only`가 **없는** 것, Node가 `.ts` 확장자를 요구하고 tsc가 그걸 거부하는 것까지 돌려보고 썼다.

계획 4·6은 그렇게 쓸 수 없다. Gmail `history.list`의 실제 응답, 채널톡 메시지 객체의 실제 필드, Bedrock 출력의 실제 형태를 **아직 한 번도 본 적이 없다.** 여기에 코드 블록을 지어 쓰면 정확해 보이지만 검증된 게 아니다. 그래서 파일 구조·인터페이스·결정·검증 방법까지만 쓰고, 코드는 계획 3이 실제 응답을 가져온 뒤에 채운다.

**계획 3이 이 프로젝트의 스파이크다.** 도메인 전체 위임이 실제로 되는지, Gmail 응답이 어떻게 생겼는지가 거기서 판가름 나고, 안 되면 계획 4·6의 전제가 바뀐다.

## 순서에 대한 두 가지

**계획 2와 3은 병렬로 갈 수 있다.** 서로 의존하지 않는다. 관리자 승인이 늦어지면 2를 먼저 하고, 승인이 빨리 나면 3부터 하는 게 낫다 — 3이 더 많은 걸 알려주기 때문이다.

**계획 1이 머지되기 전에 `src/app/admin/**`를 `main`에 올리지 않는다.** 지금 `/admin`은 404이고 그 상태가 유지돼야 한다.
