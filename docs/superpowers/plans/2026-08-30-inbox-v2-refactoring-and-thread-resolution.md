## 1. 개요 및 배경

현재 Medidakos 백오피스의 받은편지함(v2)은 다채널(Gmail Thomas/Hally, Outlook, Channel Talk) 인바운드 문의를 효율적으로 관리하기 위해 도입되었으나, 실제 운영 과정에서 다음 두 가지 구조적 문제가 확인되었습니다.

1. **스레드 파편화 및 내부 직원 식별자 오분류 (Identity Misattribution)**:
   - 외부 바이어와의 대화 중 사내 직원(`@techasset.co.kr`, `@medidakoslabs.com`)에게 포워딩(Fwd)하거나 사내 직원이 참조(Cc)된 경우, 수집기/백필 로직이 해당 스레드의 대표 식별자(`identityId`)를 사내 직원으로 잘못 추출하여 스레드가 `internal`로 격리되고 바이어 대화에서 최신 메시지가 누락되는 문제.
2. **화면 역할 불일치 및 딜 생성 워크플로우 단절**:
   - 수백 건의 인바운드를 초고속으로 분류해야 하는 **[검토함]**에 AI 제안 검토 패널이 우측 3번째 컬럼으로 배치되어 화면이 과밀해진 반면,
   - 실제 승인된 바이어와 협상하며 딜을 생성해야 하는 **[고객 업무]**에는 단순 메타 입력창(대화 인스펙터)만 존재하여 **"메시지 분석 → 제품 사양 검토 → 딜 원장 생성"**의 핵심 비즈니스 파이프라인이 단절된 문제.

본 기획서는 위 두 가지 문제를 근본적으로 해결하기 위한 **데이터 정규화 아키텍처**와 **UI/UX Pro Max 기반 2단계 워크플로우 개편안**을 정의합니다.

## 2. [문제 1] 스레드 파편화 및 Identity 오분류 해결 방안

### 2.1 문제 정의 및 재현 케이스

#### 발생 메커니즘
Gmail 수집기 및 초기 백필 로직이 스레드의 상대방(`counterparty`)을 결정할 때 첫 번째 메시지의 `to[0]` 또는 `from`을 단순 파싱하면서, 사내 직원간 포워딩 메일이 포함된 스레드에서 사내 이메일(`y@techasset.co.kr` 등)을 식별자로 오인함.

#### 확인된 대표 케이스 3종
1. **Case A: 사내 포워딩 스레드 (Division Twenty)**
   - **현상**: Hally가 바이어 문의를 사내 직원(`y@techasset.co.kr`)에게 전달한 스레드(`1a037aa19bde10ac`)에서 이후 바이어(`divisiontwenty@gmail.com`)의 회신 5건이 발생했으나, 스레드가 `email:y@techasset.co.kr`로 고정되어 `광고·내부` 탭으로 격리됨.
2. **Case B: 복수 계정/담당자 분할 스레드 (Michelle 310 Beauty Group)**
   - **현상**: 동일 바이어와 Thomas, Hally가 각각 주고받은 메일이 `email:michelle@310beautygroup.com`, `email:thomas@medidakoslabs.com`, `email:hally@medidakoslabs.com`으로 3개 파편화됨.
3. **Case C: 바이어 다중 이메일 (Finding Ferdinand)**
   - **현상**: 바이어가 `hello@findingferdinand.com`과 `o@findingferdinand.com`으로 번갈아 문의하여 대화가 나뉨.

---

### 2.2 해결 아키텍처 (Counterparty Extraction Engine 강화)

#### 원칙 1: 내부 도메인 영구 제외 (Internal Exclusion Guarantee)
- `techasset.co.kr`, `medidakoslabs.com`, `medidakos.com` 및 `BACKOFFICE_ADMIN_EMAILS`에 속한 주소는 **어떠한 경우에도 외부 상대방(`identityId`)으로 선정될 수 없음**.
- 스레드 내에 외부 참여자(External Participant)가 단 1명이라도 존재하면, 해당 스레드는 100% **외부 참여자의 이메일**을 식별자로 가짐.

#### 원칙 2: 스레드 참여자 기반 우선순위 결정 알고리즘
스레드 내 모든 메시지를 스캔하여 다음 우선순위로 `identityId`를 확정:
1. **1순위**: `direction === 'in'`인 인바운드 메시지의 발신자(`from`) 중 외부 이메일.
2. **2순위**: `direction === 'out'`인 아웃바운드 메시지의 수신자(`to`) 중 외부 이메일 (내부 도메인 제외).
3. **3순위**: 모든 참여자가 사내 도메인인 경우에만 `internal`로 분류 및 해당 직원 식별자 부여.

#### 원칙 3: 멱등성 재색인 스크립트 실행 ([`scripts/repair-thread-identities.mjs`](file:///Users/giwook/Documents/medi-da-kos/scripts/repair-thread-identities.mjs))
- 전체 673개 스레드 및 516개 identities를 재평가하여, 오분류된 9개 외부 바이어 스레드를 정상 `identityId`로 병합 갱신.

## 3. [문제 2] 2단계 딜 인큐베이션 워크플로우 및 UI 개편

### 3.1 워크플로우 재정의 (2-Stage Pipeline)

```
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│ [1단계] 검토함 (Review Queue) : 고속 트리아지 & 리드 승인                                  │
│  - 목적: 500여 건의 대기 인바운드 메일을 빠르게 검토하고 바이어/제조사/스팸 분류            │
│  - 화면: 2-Column 집중형 뷰 (인바운드 목록 30% + 대화 타임라인 및 즉시 답장 70%)           │
│  - 액션: [1] 정상 바이어 승인 (Qualified Lead) ──> 클릭 시 바이어 생성 & [고객 업무]로 승격! │
└────────────────────────────────────────┬─────────────────────────────────────────────────┘
                                         │
                                         ▼ (실시간 승격)
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│ [2단계] 고객 업무 (Customer Work) : 딜 인큐베이션 & 딜 원장 생성                           │
│  - 목적: 승인된 바이어와 본격적인 OEM/ODM 견적·스펙 협상 및 딜 파이프라인 진입               │
│  - 화면: 3-Column 일체형 뷰                                                               │
│     ├─ Column 1 (25%): 승인된 바이어 대화 목록 (SLA, 미답장 알림, 담당자)                │
│     ├─ Column 2 (42%): 바이어와의 전체 통합 대화 타임라인 & 협상 회신 입력창              │
│     └─ Column 3 (33%): [AI 제안 검토 & 딜 생성 인큐베이터]                                │
│          ├─ [스마트 메타]: 담당자(Owner), Next Action, 목표 기한(Due Date)                 │
│          ├─ [AI 추출 사양]: 품목명, 제형, 타겟 단가, MOQ, 인증 요구사항 편집               │
│          └─ [🚀 딜(Deal) 원장 생성 및 동기화]: 클릭 시 deals 원장에 즉시 등록 & 보드 연동 │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

- **주요 특징**:
  - 우측 패널에서 복잡한 AI 추출 폼을 제거하여 시야 확보 및 대화 내용 읽기 편의성 극대화.
  - 상단 `[1] 정상 바이어 승인` 버튼(단축키 `1`)을 누르면:
    1. 바이어 엔티티 자동 생성/연결.
    2. 대화 식별자가 `buyer`로 분류되고 `conversations` 컬렉션에 롤업 생성.
    3. `고객 업무` 탭으로 자동 이동하여 딜 생성 단계로 연결.

```
│   담당: Thomas Lee     │    (스레드 원문 연결 발송)            │ 탭: [제품 사양 (Items)] [바이어] [일정/인증] │
│   Next: 샘플 QC 검수   │                                      │ • 세럼 50ml (제형: 펩타이드 / 5,000개)       │
│                        │                                      │ • 수분크림 100ml (제형: 시카 / 3,000개)      │

│                        │                                      │ ──────────────────────────────────────────── │
│                        │                                      │ 🚀 [딜 원장 생성 및 파이프라인 진입]        │

```
- **기존 `대화 인스펙터`의 완벽한 흡수**:
  - 별도 분리되어 있던 담당자, Next Action, 기한 설정을 우측 딜 인큐베이터 상단 **스마트 메타 헤더**로 통합하여 공간 낭비 제거.
- **원클릭 딜 생성 및 동기화**:
  - `[🚀 딜 원장 생성 및 파이프라인 진입]` 클릭 시:
    1. Firestore `deals` 컬렉션에 새 딜 원장 자동 생성 (`stage: 1`).
    2. AI가 추출·편집한 제품 목록(`items`), 바이어 정보, 목표 일정이 딜 원장에 즉시 바인딩.
    3. 해당 대화에 `dealId`가 연결되어 딜 보드(`/admin/deals`)와 양방향 동기화 완료.

## 6. 기대 효과

1. **대화 누락 제로화 (100% Complete History)**:
   - 사내 포워딩이나 담당자 변경이 있더라도 바이어 기준 모든 대화 16건이 단절 없이 시간순으로 완벽히 병합됨.
2. **트리아지 속도 5배 향상**:
   - 검토함에서 메일 내용 확인 후 단축키 `1`번으로 즉시 고객 업무로 넘기므로, 대량의 인바운드를 수 분 만에 정리 가능.
3. **딜 전환율 및 데이터 정확도 극대화**:
   - 고객 업무에서 바이어와 대화하면서 AI가 뽑아준 제품 스펙을 바로 보고 딜을 생성하므로, 수기 입력 오류가 없고 딜 파이프라인 진입 속도가 획기적으로 단축됨.
